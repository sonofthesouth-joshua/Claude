# skill-forge (DIY)

Takes the **build queue** from your signed Friction Map and turns each candidate into a **working agent you own**: a skill (and a routine, where it recurs). The documentation is generated by studying the work — not by holding meetings. Observation gets ~80% of the way; a 10-minute interview fills the edge cases; the output is a runnable agent, not a dead SOP document.

**Hard rules (every phase):**
1. **Additive markdown only.** A forged agent is new files: `000 OS/skills/<name>/SKILL.md`, `000 OS/routines/<name>.md` (when recurring), `.claude/commands/<name>.md`. Never edit the brain core or source systems.
2. **Observe-first, consented, passive.** Study the work where it's already visible: a screen recording of one real run, the artifacts the process produces, a walk-through in the owner's words. No covert monitoring. The person should feel *watched while working*, never *pulled into a documentation meeting*.
3. **Safety envelope on every routine — non-negotiable.** `max_budget_usd`, `max_duration_sec`, `sends_external` (default `false` or `drafts_only`). **Nothing sends an external message, money, or campaign autonomously** without your explicit `sends_external: true` ruling. Default to drafts + human-in-the-loop.
4. **Engine-neutral.** Logic in vault markdown, no hardcoded model versions, budget caps declared. A skill should survive switching agent CLIs.
5. **Built ≠ works.** No agent is "done" without a passing acceptance test and a dry-run on real or realistic data — sandboxed, never mutating live data.
6. **No credentials in chat.** Keys → `api-keys.env` via a text editor.
7. **Provenance.** Each forged skill's header links the candidate (`C-xx`) and frictions (`F-xx`) it kills, so anyone can trace why the agent exists.
8. **Scope: forge + test. Scheduling is Step 4; maintenance is Step 5.** Routines ship `enabled: false`.
9. **Idempotent.** Checkpoint per candidate to `000 OS/install/skill-forge-progress.md`; candidates move independently through observe → interview → forge → test → ship.

## Inputs

- A signed-off Friction Map (Step 2) with a build queue. Missing → stop.
- The Step-1 brain (voice, tool stack, data shapes) — read-only context.
- Per candidate: a way to observe the process + the process owner for a ≤10-min interview.

## Phase 1 — Observe the workflow

For each candidate, study the **actual** workflow until the steps are concrete:

- **Narrated live run (primary):** the owner does the task once for real, narrating each step in the chat as they go ("now I copy this into the sheet…"). You capture the ordered steps, tools, and data moved, and read along in any files they touch inside the vault or share with you.
- **Artifacts:** read what the process already emits (the emails, the spreadsheet, the template, the report). Outputs reveal inputs and the transform.
- **Walk-through:** "walk me through one real example," in their words.
- *(A screen recording only helps if your agent can actually process video — most can't. Don't ask for one by default; the narrated run replaces it.)*

Write `000 OS/install/forge/<candidate>/observed-workflow.md`: **trigger**, ordered **steps** (who/what/tool/data), **decision points**, **inputs/outputs** with shapes, **frequency**. Anything unresolved becomes an open question for Phase 2.

## Phase 2 — Edge-case interview (≤10 min)

Ask ONLY the 3–4 questions observation left open:
- The exceptions: "what do you do when it's *not* the normal case?"
- The quality bar: "how do you know a good output from a bad one?"
- The judgment calls: which decisions are genuinely human and must stay human?
- The failure handling: "when this goes wrong, what breaks, and what do you do?"

Append answers to `observed-workflow.md`, tagged `interview`.

## Phase 3 — Forge the agent

Generate from the captured workflow:

- **`000 OS/skills/<name>/SKILL.md`** — the agent: purpose, trigger, inputs, ordered steps, decision rules, what-stays-human, exceptions, failure handling, acceptance test. Provenance header (Hard Rule 7).
- **`000 OS/routines/<name>.md`** — only if it recurs on a schedule. Full safety envelope (see `000 OS/routines/README.md`), `enabled: false`.
- **`.claude/commands/<name>.md`** — one-line shim pointing at the skill.

Mark the skill **beta** until it passes Phase 4.

## Phase 4 — Test

- Run the acceptance test + a dry-run on real or realistic data, read-only/sandboxed. Compare the output with what the process owner actually produces.
- Review against the observed workflow + edge-case answers. Iterate until the dry-run output is correct.
- Then have the process owner watch the agent do their work once. Capture corrections, iterate. Explicitly confirm what-stays-human, and any `sends_external` permission (an agent that sends on your behalf gets an explicit, logged yes — never a silent default).

## Phase 5 — Ship

- Remove the beta marker, commit the new files, log the result in `000 OS/install/skill-forge-progress.md` and `210 Runs/`.
- The agent now appears in your dashboard (Step 4) automatically — the dashboard reads the skills and routines folders.
- Leave routines `enabled: false`; you flip them on in the dashboard once scheduled runs are set up (Step 4).

## Acceptance test (the step is done when)

- [ ] Every build-queue candidate is **shipped** (observed → interviewed → forged → tested → owner-reviewed) or **parked** with a written reason
- [ ] Every shipped routine declares the full safety envelope; any `sends_external: true` has a logged owner approval
- [ ] Nothing mutated the brain core or live business data; all changes additive
- [ ] Run line in `210 Runs/`

**Next:** Step 4 — stand up the dashboard (`guides/step-4-dashboard.md`).
